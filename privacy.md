# Privacy boundary

This case study describes contracted migration work without publishing the employer's automation estate.

## Published

- Aggregate inventory and migration counts.
- Generic examples of defects found through comparison.
- High-level data-flow and validation model.
- Performance examples expressed without customer or record identity.
- The distinction between rebuilt, validated, and activated.

## Not published

- Customer names, contact information, domains, channels, or records.
- Make blueprint exports, module IDs, field IDs, database identifiers, or URLs.
- API keys, tokens, webhook URLs, connection details, or secret storage paths.
- Slack message text, Drive paths, Airtable base IDs, or production screenshots.
- Reusable code or step-by-step instructions that could reproduce the employer's workflows.

## Why this boundary exists

The value of the work is in the migration reasoning, defect detection, and operational safeguards. Publishing the actual blueprints would expose employer infrastructure and would make the portfolio less trustworthy, not more.
